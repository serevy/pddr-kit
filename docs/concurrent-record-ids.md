# 並行PRでのPDDR採番と衝突解消

PDDRの番号（例: \`PDDR-0013\`）は、**対象リポジトリで一意**にします。ただし複数のAgentや人間が同時にPRを作る場合、各ブランチのローカルな\`validate\`が成功しても、他の未マージPRで同じ番号を使っている可能性があります。\`validate\`はチェックアウトされた作業ツリーを検査し、GitHubのOpen PR全体を問い合わせる機能ではありません。

## 採番する前に

1. 導入先の**マージ先ブランチ**（\`main\`、\`develop\`など）を最新化し、そこにあるPDDR番号を確認します。
2. **Open PR**に追加・変更されるPDDR番号も確認します。GitHubを使うならPR一覧や変更ファイル、API/CLI（利用できる場合）で調べます。
3. 既存の番号から最大値+1を仮の候補にし、Open PRとの衝突を再確認します。**確認は番号の予約ではありません**。同時実行する複数のAgentが同じ番号を採るraceは残ります。
4. 可能なら同じ作業のPDDR候補を1本のPRへ集約し、既存PDDRの更新で足りる場合は新規採番しません。番号が競合しても、別々の判断を無理に1件へまとめません。

## マージ前に

- 他のPRが先にマージされた場合は、最新のbaseを取り込み、\`python .pddr/pddr.py validate\`を再実行します。
- 必須CIが最新baseで成功することを確認します。strict required status checksやMerge Queueを利用できる環境では、その設定を維持します。古いbaseの成功checkだけを衝突防止の保証として扱いません。
- 単一ブランチ上に両方の記録が揃った段階で、同じ\`id\`が2つ存在すれば\`validate\`が失敗します。**Gitが同じファイル名を衝突させる場合**は内容を手動解決し、異なるファイル名でも同じfront matter IDなら番号を直します。

## 衝突した場合

まだマージされていない側の番号を採り直し、**ファイル名とfront matter \`id\`**、Markdown見出し、\`related\` / \`supersedes\` / \`superseded_by\`、ほかの記録やPR/Issue本文からの参照リンクを必要に応じて一貫して更新します。元の判断、承認証拠、実装証拠を採番変更のついでに書き換えません。

baseを取り込んだ後にCIを再実行し、双方の記録と参照の整合性を確認してからマージします。自動マージや並列処理の多い導入先では、競合があればマージを止めるか直列化する仕組みも検討してください。

\`PDDR-NNNN\`形式は現時点で変更しません。原子的な中央採番器やGitHub APIへの依存は、運用で必要になったときに別途検討します。

## 回帰テスト

\`tests/test_pddr_cli.py\`の\`ParallelIdTests\`では、同じbaseから派生した2つの作業ツリーでは同じ次番号が**それぞれ検証を通過する**一方、両方の変更を含むツリーでは重複エラーとなり、保留側を採番し直すと成功することを確認します。これはPRイベントやMerge Queueそのものをシミュレートするテストではありません。
